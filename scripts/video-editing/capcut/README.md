## Decision

**A bounded CapCut-first workflow is now technically viable in installed CapCut 9.6, but staff handoff remains unproven.** CapCut 9.1 created and duplicated a synthetic project. `capcut-cli` 0.31.1 added editable media/title tracks to the copy while the app was closed. The normal launcher opened that exact copy in installed **9.6.0.4097**: the new clip appeared, its native text panel allowed editing, the timeline played, the edit survived save/close/reopen, and CapCut exported a valid local MP4. A second 12-second native export included three cut scenes, synthetic audio and a visibly moving foreground graphic. The text rendered above the foreground, so the behind-person effect failed. Copied projects retain absolute media paths and need explicit staging/relinking; another editor's machine has not been tested. Keep Nolan's proven Premiere master and Python/FFmpeg checks while this remains a synthetic compatibility proof.

### Media copy/relink result

CapCut/CLI media references are absolute. A copy of the expanded app draft in ignored `scratch/portable-native-a` initially identified **five** external materials (the native first scene plus CLI media); `capcut lint --fix --active-timeline` staged all five into that disposable copy's `assets/`, leaving a clean local lint result. Copying that folder again to `scratch/portable-native-b` retained paths to A: lint reported five `media-outside-draft` items despite the copied files being present. `capcut relink B --from <absolute A> --to <absolute B> --active-timeline` changed all five paths, found five present files and zero missing/ambiguous files; lint then passed with zero findings. This proves a **local path repair**, not native project registration or a second editor's save/reopen. Packaging/relink instructions and a fresh-machine CapCut test are required before promising staff shareability. Do not assume a simple folder copy is portable.

### Practical conclusion and next gate

The proved seam is: **native app-created draft → closed-app CLI edit of a protected duplicate → exact-name native reopen → editable text review → native save/reopen → local CapCut export → decode/frame/audio checks.** This is enough for a controlled staff-assisted CapCut pilot on disposable or approved assets in **9.6**, with Nolan's Python/FFmpeg checks reused for analysis. It does not justify automated production publishing, app-version-independent compatibility, compositing claims, or a cross-editor handoff. The next bounded test is a truly separate Windows editor/profile opening a relinked copy with its media, then manually editing and exporting it; independently design/approve a native foreground-over-text layout if that creative effect is required. Keep the official account-connected plugin uninstalled unless its permissions, data path and credit limits are approved.
