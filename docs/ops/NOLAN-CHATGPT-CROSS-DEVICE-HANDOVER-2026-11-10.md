## 5. Reference video link -> reusable skill (owner's preferred workflow)
**Trigger:** owner sends a video link and asks to learn an effect or to “go build the skill so it can be used in editing going forward.”
1. **Identify and examine the actual reference.** Record URL, title/creator if identifiable, date, accessibility, rights and which frames/audio were actually viewable. If the source/video/sound is inaccessible, state the exact limitation and request a permitted original/screen recording if essential; do not invent a sound or transition based on a title.
2. **Describe the technique instead of copying the video.** Identify the precise event (hook, source motion, type, composition, masking, sound/transient/beat, UI state, exit and payoff). Use frame timestamps/screens/notes and distinguish observed behaviour from a guessed creator method. Do not reproduce protected music or third-party creative assets without permission.
3. **Search the 53-card catalogue and status first.** Reuse or extend a relevant existing family, with an explicit integration plan, rather than creating a near-duplicate “new skill.” If it is genuinely new, create a versioned narrowly scoped card with prerequisites, inputs, tested parameters, known failure cases and a runnable implementation.
4. **Build in normal ChatGPT on an authorised computer.** Use connected Desktop Commander terminal/files, local Python/Pillow/OpenCV/FFmpeg or an appropriate native editor and GitHub contents/branch tools. Codex is NOT inherently necessary to write code, run commands, create a test fixture, commit documentation and connect the skill to a local renderer. Keep execution isolated, low priority while staff work, and never overwrite a client edit or install speculative packages without review.
5. **Prove the mechanism.** Choose cleared practice moving footage; output a plain control and effect candidate; inspect full decoded frame sequence, first/middle/end and boundary frames, orientation, safe type bounds, unwanted duplicates and source action. Test technical sound (stream, peaks, tails, synchrony); separate documented unobserved music/phone/native/perceptual gates. Include a rejected/negative control. A test render proves execution only.
6. **Integrate with the existing editor.** Publish source code, skill card, exact invocation, selected parameters and test/QA receipts on the existing PR910 branch after checking head/owner and conflicts. Add to the source-to-edit manifest, status board and tutorial index; compare a real owner-authorised client use where appropriate, preserving before/after and feedback. Do not create a parallel engine or shadow skill registry.
7. **Install and qualify per device.** At an idle, authorised boundary, run canonical safe backup/sync; prove library `CURRENT`, module imports, FFmpeg/native editor and one actual output/decode on Katana/Desktop/MSI separately. Transfer only authorised assets; a Git commit alone does not install a workstation, expose new global ChatGPT tools or acquire models/fonts.
8. **Promote only after evidence.** Record statuses e.g. `RESEARCH_ONLY`, `TECHNIQUE_TESTED`, `DEVICE_TESTED`, `CLIENT_CANDIDATE`, `OWNER_APPROVED`, `NATIVE_PROJECT_VERIFIED`; do not equate tested with mastered. Preserve failed and unsuitable recipes so the next editor avoids repeating them.

## 7. Sound, quality and restrictions
- **Working technical layers:** encoded audio/video probe, PCM/AAC checks, LUFS/true peak/silence/coverage, audio-stem handling and precise cue timing can be implemented with existing FFmpeg, Python and shared sound operators. Match every proposed effect to visible motivation; avoid generic whooshes, endless piano/ding motifs, bad mood mismatch, repeated client soundtracks and music from excluded/rejected ledger entries. The owner specifically rejected Tobich music that sounded disturbing/horror-like; cue character and variety must be reviewed before client delivery.
- **Not qualified on all devices:** local heavyweight CLAP/MOSS-style acoustic/music-character models, real South African/Afrikaans pronunciation, full voice-note multilingual accuracy, human creative listening and physical-phone/native project acceptance. Installed libraries or numerical tags do not clear these. Respect device-specific GPU, disk and licence restrictions; no secret/media upload to external model services to bypass a gap.
- **Editorial floor:** strong footage from first camera motion; useful action and quality selects, unique original recordings, clear colour/exposure match, unwarped people, actual brand typography, consistent text spacing, professional SFX placement, licensed music and genuine narrative arc. Review the actual final ~5 seconds including official logo and audio; don't add flash cuts that contain sideways portrait footage or irrelevant stock just to raise cut count.
- **Release:** preserve original/canonical and prior approved master, create new numbered review candidate, exact final-frame/audio tests, cover/caption/checklist; internal owner review before approved portal/WhatsApp/client send, unless explicit new authority. Never claim a reviewer heard audio/used a phone/native editor without witnessed evidence.
